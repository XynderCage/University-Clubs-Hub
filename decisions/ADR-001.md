# ADR-001: Client–Server Architecture

## Status
Accepted

## Date
25 September 2026

## Context

The University Clubs Hub allows university community members to search
for clubs and access club information. Administrative staff verify club
information and manage venue requests and booking decisions.

The main architectural quality drivers are performance, reliability
and scalability.

The system must return club search results within 3 seconds and must
correctly persist all successfully submitted booking decisions.

The architecture should also provide a practical way to support
increasing numbers of users and requests.

## Decision

The University Clubs Hub will use a Client–Server architecture.

Users will interact with the system through a web client.

The client will send requests to a central application server.

The server will be responsible for:

- club search;
- club management;
- venue requests;
- booking decisions;
- administration;
- authentication and authorization;
- database access.

The central database will store authoritative application data.

## Alternatives

### MVC

MVC separates an application into Model, View and Controller
responsibilities.

It provides good separation between presentation, user input and
application state.

However, MVC does not by itself define deployment, scalability,
network boundaries or server failure behaviour.

MVC may still be used internally but was not selected as the overall
architectural model.

### Microservices

The system could be separated into independently deployed services such
as Search, Club Management, Venue Booking and Identity.

Microservices would allow individual capabilities to scale and deploy
independently.

However, they would introduce service-to-service network communication,
distributed failure, more complex data consistency, monitoring and
deployment requirements.

The current project does not provide sufficient evidence that this
additional complexity is required.

## Positive Consequences

- Centralized application processing.
- Centralized authoritative data.
- Search and database access can be optimized on the server.
- Booking decisions can use reliable database transactions.
- Business and validation rules are applied consistently.
- Clients remain lightweight.
- Server capacity can be increased as user demand grows.

## Negative Consequences

- Clients depend on a network connection to the server.
- Network latency contributes to response time.
- Server failure may affect all users.
- Database failure may affect the entire application.
- The application server may become a scalability bottleneck.
- Individual capabilities cannot initially scale independently.

## Evidence Required

- Search performance tests confirming results are returned within
  3 seconds.
- Booking tests confirming successful decisions are persisted correctly.
- Load testing showing server behaviour as user numbers increase.
- Monitoring of server and database utilization.
- Failure testing for server, database and network outages.

## Risks

The highest architectural risk is that the central server or database
could become a bottleneck as system traffic grows.

Search performance must therefore be tested as both user traffic and
club data increase.

## Revisit When

The architecture should be reconsidered when:

- search consistently exceeds the 3-second target;
- the application server becomes a demonstrated bottleneck;
- database performance cannot support increasing demand;
- one capability requires significantly different scaling;
- independent deployment becomes necessary;
- distributed services provide benefits that outweigh their additional
  operational complexity.
